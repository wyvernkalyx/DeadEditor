## Bug 1: File Lock IOException During Import

**Status:** Fixed

**Evidence:**

Commit `f99f172` ("feat: Write custom FLAC/ID3v2 tags on import + import robustness") added comprehensive retry logic. The current code in `LibraryImportService.cs` has:

1. **`CopyFileWithRetry`** (line 167–181) — retries `File.Copy` up to 3 times with 500ms delay, catching `IOException` on each attempt.

2. **`WriteMetadataWithRetry`** (line 190–309) — retries the entire open-modify-save sequence (TagLib `File.Create` → modify → `Save`) up to 3 times with 500ms delay. Each retry opens a fresh file handle.

3. **All TagLib handles properly disposed** — every `TagLib.File.Create()` call is wrapped in a `using` block:
   - Read original metadata: `LibraryImportService.cs:108` — `using (var originalFile = TagLib.File.Create(...))`
   - Write metadata: `LibraryImportService.cs:199` — `using (var file = TagLib.File.Create(targetPath))`
   - `MetadataService.WriteMetadata`: line 334 — `using (var file = TagLib.File.Create(track.FilePath))`
   - `MetadataService.ReadAlbumInfo`: line 219 — `using (var file = TagLib.File.Create(firstFile))`

4. **Workflow is safe**: read handle (source file) is disposed before copy, then write handle (target file) is opened fresh with retry logic.

**Confidence:** High — code inspection shows all TagLib handles are in `using` blocks, and the retry mechanism handles transient Windows file locks (Defender, indexer, NTFS journal).

**Notes:** If IOException still occurs in edge cases, the fix would be to increase retry delays from 500ms to 1000–2000ms. The underlying code pattern is correct.

## Bug 2: Data Corruption in Edit Metadata Type Conversion

**Status:** Still present

**Evidence:**

The type conversion from Audience Recording to Official Release has **no data migration logic**. The save workflow blindly writes per-track dates regardless of album type, and the library display then fragments the album by date.

**The corruption chain:**

1. **Save writes track-level dates unconditionally** — `MetadataService.cs:342`:
   ```csharp
   var date = !string.IsNullOrEmpty(track.PerformanceDate)
       ? track.PerformanceDate : album.AlbumDate;
   ```
   This uses per-track dates (PerformanceDate = TrackDate) if present, regardless of album type. For a multi-date Official Release like "Road Trips Vol. 2 No. 2", tracks retain their original concert dates (e.g., "1968-02-14", "1968-02-16", "1968-02-18") in the TITLE tag.

2. **ALBUMTYPE tag is updated** — `MetadataService.cs:411`: `xiph.SetField("ALBUMTYPE", album.Type.ToString())` correctly writes "OfficialRelease".

3. **Library reload extracts all dates** — `LibraryShow.cs:126–138`: `ExtractDatesFromTitles()` uses regex `\((\d{4}-\d{2}-\d{2})` to extract every distinct date from TITLE tags. Multi-date albums yield 3+ dates.

4. **"By Date" view fragments the album** — `LibraryGridView.xaml.cs:471–488`: `BuildDateRows()` creates a separate grid row for each extracted date when `dates.Count > 1`. One album becomes multiple entries.

5. **No type-transition handling in save** — `EditMetadataView.xaml.cs:519–568`: The code detects `typeChanged` (line 519) but only shows an informational MessageBox (line 559). No data migration occurs — TrackDate fields are not cleared, TITLE tag dates are not adjusted, and no re-grouping happens.

**What's missing:**
- When converting Audience Recording → Official Release: should either clear TrackDate fields or ensure the library display doesn't fragment multi-date Official Releases
- When converting Official Release → Audience Recording: should ensure TrackDate is populated for all tracks

**Confidence:** High — the save code path has no album-type-aware date handling, confirmed by direct code inspection.

**Notes:** The fix should likely be in `MetadataService.WriteMetadata` or in how `BuildDateRows` handles Official Release albums. The simplest approach: `BuildDateRows` should check album type and never fragment Official Releases, regardless of how many dates appear in track titles.

## Bug 3: NullReferenceException on Startup

**Status:** Still present

**Evidence:**

The NRE is in `ShowLookupService.ShowInfo.FormattedLocation` (line 58–65):
```csharp
public string FormattedLocation
{
    get
    {
        if (!string.IsNullOrEmpty(State) && Country == "US")
            return $"{City}, {State}";
        return $"{City}, {Country}";  // ← NRE when City or Country is null
    }
}
```

This property lacks null guards on `City` and `Country`. When `Country` is null (possible from JSON deserialization of incomplete show data), string interpolation itself won't throw, but **downstream code** that calls `.Contains()`, `.StartsWith()`, etc. on the result will throw if the property returns `null`.

**However**, the more likely NRE path at ~851ms into startup:
1. `ShellWindow` constructor navigates to Library view (line 62)
2. `LibraryGridView_Loaded` fires → calls `LoadShowsAsync()` (line 67)
3. `LoadShowsAsync` scans albums on background thread, returns to UI thread
4. `BuildDateRows()` (line 121) or `BuildMissingShowRows()` (line 129) runs
5. These call `ShowLookupService.Instance.GetShowByDate()` and access `.FormattedLocation`
6. If any show in `shows.json` has null `City` or `Country` → NRE

**The fix already exists in ConcertReference.cs** (lines 27–35):
```csharp
if (!string.IsNullOrEmpty(State) && Country == "US")
    return $"{City}, {State}";
if (!string.IsNullOrEmpty(Country))          // ← Guard
    return $"{City}, {Country}";
return City;                                  // ← Fallback
```

The same defensive pattern needs to be applied to `ShowLookupService.ShowInfo.FormattedLocation` at line 58.

**Confidence:** High — the unguarded property is confirmed at `ShowLookupService.cs:58–65`, and the fixed version in `ConcertReference.cs:27–35` proves the team already identified this pattern.

**Notes:** This is a one-line fix: add the same null/empty check on `Country` that `ConcertReference` already has. No git commits were found addressing this specific NRE.

## Bug 4: Grid Render Delay (60 seconds)

**Status:** Fixed

**Evidence:**

Commit `a664e63` ("perf: Fix 60-second grid render delay caused by heady icon binding") resolved this.

**Root cause was:** The `HeadyIcon` property binding in the DataGrid's heady column triggered `ContainsDates` → `TrackTitles` → `LoadTrackTitlesFromDisk()`, which opened every FLAC/MP3 file in the library with TagLib. This happened synchronously on the UI thread during grid rendering (~930 files x ~40ms each = ~37 seconds).

**Current fix** in `LibraryShow.cs` (lines 155–173): The `HeadyIcon` property getter now:
1. Uses a **fast path** — checks `show.Date` against `HeadyVersionService` without lazy-loading
2. Guards lazy-load with `if (_containsDatesLoaded && _containsDates != null)` — only checks `ContainsDates` if already loaded, never triggers the lazy-load during binding

Related commit `297e361` ("fix: Shows I Don't Have UI freeze — guard lazy-load and async computation") also added guards for a similar freeze in the "Shows I Don't Have" feature.

**Confidence:** High — the fix commit is confirmed, and the guard pattern is present in the current code.

**Notes:** The grid currently has no explicit `VirtualizingStackPanel` settings in XAML but relies on DataGrid's default row virtualization, which is sufficient.

## Bug 5: Segue Marker Multiplication

**Status:** Fixed

**Evidence:**

Commit `4e4278d` ("fix: Album name not persisting after save + segue markers multiplying") resolved this.

**Root cause was:** In EDIT MODE, `ReadFolder` loads FLAC titles as-is without stripping segue markers (by design — edit mode preserves raw tags). So `SongName` contained the marker: `"Dark Star >"`. When `WriteMetadata` then appended another `" >"` for `HasSegue == true`, the title became `"Dark Star > >"`. Each save cycle added another marker.

**Current fix** at `MetadataService.cs:356–358`:
```csharp
// Strip any existing segue markers to prevent multiplication on repeated saves
// Handles: " >", " > >", " > > > >" etc.
title = Regex.Replace(title, @"(\s*>)+\s*$", "").TrimEnd();
```

This runs immediately before the conditional append at line 361–364:
```csharp
if (track.HasSegue)
{
    title = title + " >";
}
```

The same pattern was applied in `EditMetadataView.ReconstructRawTitles` (line 664) for consistency.

**Confidence:** High — the strip-before-append pattern at line 356–358 makes the write operation idempotent. Confirmed by code inspection.

**Notes:** IMPORT MODE was already safe because `ParseTitleAndDate` strips segue markers during title parsing (lines 511, 531, 551, 574, 608, 625, 631). The fix was specifically needed for EDIT MODE's as-is title loading.
